# Two-release migration review — v0.3.0 ↔ v1.0.0 (E14 S5, runbook §2 item 3)

**Scope:** release N+1 (`v1.0.0`) migrations keep release N (`v0.3.0`) runnable, and vice versa.
Blue and green share the database (runbook §3) — this review is the expand/contract audit the
checklist demands, executed against the REAL V-table, not a narrative.

## Method (empirical, not prose)

1. `git diff --name-status v0.3.0..main -- modules/*/src/main/resources/db/migration/` — the full
   migration delta: 11 files (10 added, 1 content-changed).
2. `scripts/deploy.sh --check HEAD` (TD-33 gate): `migration-gate PASS — 11 migration files,
   11 allowed-with-log relaxation(s)` + `DB cross-check OK — flyway_schema_history within
   v0.3.0..HEAD`.
3. **The decisive two-release test**: boot v1.0.0 code against a database carrying the GENUINE
   v0.3.0 history. Reproduced by applying the v0.3.0 migration set (V101–V106, V201, V301 as
   shipped in v0.3.0) through Flyway 12.4.0 (same version as the app) into a fresh Postgres 16,
   then starting the v1.0.0 image against it.

## Finding F1 (blocker for real v0.3.0 deployments) — empirical evidence

`V301__create_notifications_schema.sql` was modified after v0.3.0 (E10 S1, commit `30245af`)
adding the `notifications.notification` table **without a new version number**. The v0.3.0 file
created only the schema; the v1.0.0 file also creates the table.

Verified against the genuine v0.3.0 history (Flyway 12.4.0, fresh Postgres 16):

```
$ boot v1.0.0 image against the v0.3.0-migrated database
ERROR ... Failed to initialize dependency 'flywayInitializer' ... Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 301
Either revert the changes to the migration, or run repair to update the schema history.
```

Consequences for a real v0.3.0→v1.0.0 upgrade:
1. **v1.0.0 code refuses to boot** (Flyway validate fails on the V301 checksum mismatch).
2. Even after a `flyway repair` (checksum realignment), the `notifications.notification` table
   is never created (V301 is marked applied) → the notifications consumer fails on first insert.

Impact scope: honest and narrow — **no production v0.3.0 deployment exists** (v0.3.0 was a local
milestone tag; the only databases are dev/CI volumes initialized from later trees, where V301
applied with its final content). The defect blocks the UPGRADE PATH, not any live system.

## Remedy options (owner decision — Amendment (d) class; not resolved in-block)

- **(a) Recommended:** revert `V301` to its v0.3.0 content (schema-only) and add
  `V302__notification_table.sql` carrying the table DDL (forward-only, additive). Fresh databases
  apply V301→V302 identically; v0.3.0 databases validate cleanly and receive V302 at upgrade.
  Cost: one new migration file + reverting one file to its historical content. This is the
  standard Flyway remedy (never modify an applied migration; always add).
- **(b) Accept and document:** declare v1.0.0 a fresh-install-only release (true today — no
  v0.3.0 production DB exists), record the V301 history defect as known debt with the upgrade
  instruction (manual `flyway repair` + manual table creation, or dump/restore via
  `scripts/backup.sh`/`restore.sh`, which sidesteps migration history entirely).

## F1 round 2 — owner adjudication (2026-09-07, supersedes remedy options above)

The earlier remedy (a) — revert `V301` to its v0.3.0 content and add `V302` — was **rejected by the
owner after round-2 evidence** (dated "F1 round 2 — ADJUDICADO: A'", Emenda (e), the second
evidence-over-will event). The round-2 finding, proven empirically with the same harness:

> **One migration file has exactly one checksum.** The v0.3.0 `V301` (schema-only) and the current
> `V301` (schema + table) are *different files* from Flyway's point of view. Reverting `V301`
> breaks every database that already applied the full-content `V301` (dev, CI, drill — the only
> databases that exist) with the identical `Migration checksum mismatch for migration version 301`
> the fix aimed to remove. No single `V301` file can validate against BOTH histories. Since no
> v0.3.0 production database exists, reverting repairs zero deployments and breaks them all.

Round 2 evidence (reproduced, Flyway 12.4.0 / Postgres 16.15):

| Scenario | File set | Result |
|---|---|---|
| Later-tree DB (full-content V301 applied) → **reverted V301 + V302** | attempted fix | ❌ `Migration checksum mismatch for migration version 301` |
| Later-tree DB (full-content V301 applied) → **unchanged V301** | shipped | ✅ validates, 0 new migrations |
| Genuine v0.3.0 DB → unchanged full V301 | shipped | ❌ checksum mismatch (known, no such DB exists) |

## Adjudicated disposition (A') — what actually ships

- **V301 stays as-is (full content).** No revert, no `V302`. Every real database validates and boots.
- **Direct v0.3.0 → v1.0.0 migration is UNSUPPORTED.** v0.3.0 was a local milestone tag with zero
  production deployments; the Flyway immutability contract makes the upgrade path un-crossable
  without breaking immutable history. Declared, not hidden.
- **Supported upgrade path for any hypothetical v0.3.0 data = data-only dump/restore:**
  1. `pg_dump --data-only --exclude-table-data=public.flyway_schema_history` (custom or plain SQL)
     on the v0.3.0 database.
  2. Boot a **fresh** v1.0.0 stack (Flyway applies the full 18-migration chain; the additive policy
     guarantees the new schema is a superset of what v0.3.0 created).
  3. Load the data-only dump into the fresh database.
  4. Run the restore verification: per-table counts + balance proof (`scripts/restore.sh` logic).
  A **full-dump restore must NOT be used** — it carries the old checksummed history and fails
  validation on boot.

### Rehearsal (proven locally, 2026-09-07)

Genuine v0.3.0 DB seeded (2 payments, 1 api key, 1 idempotency, 1 outbox, 1 audit log) →
`pg_dump --data-only` (history excluded) → fresh v1.0.0 boot (18/18 migrations validated) → data
loaded (COPY 1/1/2 clean) → verification:

```
payments.payments 2 | api_keys 1 | idempotency_keys 1 | outbox 1 | audit_log 1   (identical)
flyway_schema_history: 18 rows, pristine v1.0.0 chain (no leakage)
balance proof: Σ DR = Σ CR = 0 ; projection drift 0
```

> **Two-release migration review (v0.3.0 ↔ v1.0.0): PASS with two dispositions. Ten of eleven

> single contract violation — V301 content changed post-v0.3.0 without a version bump) is resolved

> v0.3.0 → v1.0.0 migration is declared UNSUPPORTED (no v0.3.0 production deployment exists); the

> proven by local rehearsal.**

## Vice-versa direction (v1.0.0-built state runnable by v0.3.0 code)

Reverse compatibility is structurally guaranteed by the additive verdicts above: v0.3.0 code
runs against the v1.0.0 schema unchanged (it references only tables/columns that existed at
v0.3.0; all v1.0.0 changes are new objects or constraint relaxations). Blue-green share the
database during a deploy window exactly under this contract: old fleet (v0.3.0-shaped reads)
and new fleet (v1.0.0) coexist on the expanded schema. F1 does not affect this direction
(v0.3.0 code never reads `notifications.notification`).
