# PITR rehearsal — 2026-09-08 (E15 S5)

The dump drill (E14 S4 / E15 S4) proves restore-from-file. **PITR is the other half of the
recovery story**: replaying WAL to a point in time. This rehearsal proves the mechanism and
measures the achieved RPO window — locally, honestly, per the Q-batch decision below.

## Q-batch decision (2026-09-08)

**Local-documented-only.** The dump drill stays the CI-dispatched artifact (`restore-drill`,
`restore-drill-scale`); PITR is a harness (`scripts/pitr-rehearsal.sh`) + this record. The
record says which: local. Rationale: the mechanism (archive_mode + pg_basebackup + WAL replay +
`recovery_target_lsn`) is Postgres-generic — CI-ifying it adds runner minutes without adding
guarantee; the runbook keeps the procedure, this record keeps the proof it works.

## Harness procedure (scripts/pitr-rehearsal.sh, P0–P7)

| Phase | What happens |
|---|---|
| P0 | Standalone `postgres:16` container with `archive_mode=on`, `archive_command` → host WAL dir, `archive_timeout=5s` |
| P1 | Minimal schema (payments + ledger) + **seed A**: 3 000 CONFIRMED payments, each 1 event + 1 journal entry + 3 postings (DR processing / CR fees / CR merchant avail) — balanced by construction |
| P2 | `pg_basebackup -Ft -z -X stream` → base snapshot (base.tar.gz + pg_wal.tar.gz) |
| P3 | **Side effects AFTER the base**: +1 500 payments (seed B, same balanced shape); capture `recovery_target_lsn` = WAL insert LSN of the last committed seed-b txn, THEN `pg_switch_wal()` so the containing segment is archived |
| P4 | **Hard kill** — `docker kill -s 9` (no clean shutdown; only base + archived WAL remain) |
| P5 | New cluster from the base tars; `restore_command` ← archive dir; `recovery_target_lsn`, `recovery_target_action=pause`, **`recovery.signal` marker (PG16 mandatory)**; server enters recovery, replays WAL, pauses at target |
| P6 | Validation AT THE RECOVERED STATE (read-only, in-recovery): counts, ΣDR=ΣCR, projection==lines |
| P7 | Teardown (container, network, scratch) |

## Limits (declared, not hidden)

- **Local host volume assumptions**: WAL archive on the same filesystem as the base backup —
  a REAL disaster (host loss) requires the archive off-host (that is the runbook §6 unit
  gap this record surfaces, recorded as such — not solved here).
- Volume class is modest (4.5k txns); the S4 scale drill covers volume for the DUMP path. WAL
  replay cost scales with post-base WAL volume, not row count — this run's ~1 s replay is for
  ~1 500 txns of WAL.
- Harness uses a minimal schema materialized by SQL (no Flyway) — it proves the RECOVERY
  MECHANISM (archive → base → replay → target → pause → validate), not the app's migration path.

## Gotchas carved into the harness (born from this rehearsal — AGENTS amendment (f))

1. **Readiness probes must use TCP** (`psql -h 127.0.0.1`): the docker-library postgres
   entrypoint boots a throwaway socket-only server for initdb that is fast-stopped right
   before the real one — a socket probe can hit it and die with "shutting down"
   (docker-library/postgres#146).
2. **PG16 requires `recovery.signal`** in the data dir or the server boots NORMAL —
   `restore_command` alone is ignored, recovery silently doesn't happen (PG docs §26.3.4 step 7).
3. **`recovery_target_lsn` must sit inside a COMPLETED (archived) segment**: capture it BEFORE
   `pg_switch_wal()`, and never use a wall-clock timestamp captured from the shell after the
   last commit — it can land past the archived WAL's end and PG16 dies with "recovery ended
   before configured recovery target was reached".
