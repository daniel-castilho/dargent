# PITR v2 rehearsal — 2026-09-08 (E16 S2 — off-disk WAL)

v1 (`docs/drills/pitr-2026-09-08.md`) proved the WAL-replay mechanism with the archive on the
SAME host directory as everything else — declared limit: *"a REAL disaster (host loss) requires
the archive off-host"*. **v2 answers that caveat the way compose can honestly prove it**: the WAL
archive and the base snapshot live on **separate docker volumes**, and the disaster is the
**destruction of the Postgres data volume itself** (`docker volume rm`) — not just a container kill.

## What changed vs v1

| Property | v1 (E15 S5) | v2 (this) |
|---|---|---|
| WAL archive location | bind-mounted host dir (same filesystem as the cluster dirs) | **dedicated named volume** (`dargent-pitr-v2-wal`) — separate host subtree |
| Base snapshot | host dir | **dedicated named volume** (`dargent-pitr-v2-base`) |
| Disaster | `kill -9` the container (data dir intact) | `kill -9` **AND `docker volume rm` the pgdata volume** — the database disk is GONE |
| Survivors | data dir + archive + base (same disk) | **base + wal volumes only** (the pgdata volume no longer exists) |
| Restored onto | same host dir | **a fresh pgdata volume** created after the disaster |

## Procedure (scripts/pitr-rehearsal-v2.sh, P0–P7)

P0 named volumes (pgdata/wal/base) — **the wal volume is chmod 0777 before the primary boots**:
a fresh named volume mounts root-owned and every `archive_command` copy fails with EACCES
(`pg_stat_archiver.failed_count` climbs, archive stays empty — found by measurement, fixed once).
Primary boots with `archive_mode=on`, `archive_command='test ! -f /wal-archive/%f && cp %p
/wal-archive/%f'`, `archive_timeout=5s` → P1 seed A (3 000 balanced txns, consumer posting shape)
→ P2 `pg_basebackup -Ft -X stream`, tars staged into the **base volume** → P3 post-base side
effects (+1 500 txns), `recovery_target_lsn` captured BEFORE the segment switch (E15 lesson),
`pg_switch_wal()` → **P4 `kill -9` + `docker volume rm` pgdata** → P5 fresh pgdata volume, base
tars + `restore_command` from the wal volume (ro), `recovery.signal`, `recovery_target_lsn`,
`recovery_target_action=pause` → P6 validation at the recovered state → P7 measured RPO + teardown.

- The volumes share the HOST: this proves the archive survives the **death of the database
  volume**, not host loss. The production posture (off-host/NFS archive) is the runbook §6 unit
  this rehearsal models; `deploy/systemd/postgres-wal-archival.conf` (15-min policy) is the
  shipped config surface for it.
- Volume class modest (4.5k txns) — WAL replay cost scales with post-base WAL volume, not row
  count (v1 finding, unchanged).
- Harness uses a minimal SQL-materialized schema (no Flyway) — it proves the RECOVERY MECHANISM,
  not the app's migration path.

## Gotchas carved this round (amendment (f) — each found by one doc/measurement lookup)

1. **Fresh named docker volumes mount root-owned (0755)** — the postgres uid cannot write the
   archive; `pg_stat_archiver.failed_count` climbs silently while `archived_count` stays 0. The
   volume needs `chmod 0777` (or chown 999) BEFORE the primary boots.
2. Canonical file names matter more than they look: staging `pitr-v2-base.tar.gz` while the
   recovery reads `base.tar.gz` — `ls` shows files, `stat` says ENOENT; the ls output WAS the
   evidence (three debug rounds spent before reading it properly).
